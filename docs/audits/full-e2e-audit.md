Shared rules for every agent (from the audit brief): stay inside your files and list any cross-ownership edit; fix bugs test-first; never weaken, skip or delete a test; every number must come from a command that was run; small conventional commits; `pnpm typecheck`, `pnpm lint`, `pnpm format:check` and `pnpm test` must pass before the final commit.

### 2.2 Reviews

1. **One independent reviewer per workstream**, read-only, with its own ports. Each review produced a verdict, findings with file and line, and a concrete fix. The implementer fixed the findings test-first; the reviewer re-reviewed the fix round. W1 needed two re-reviews, the others one; W2's, W4's and W5's last small rounds were checked by the controller, and W6's second round was re-reviewed by the final frontend reviewer.
2. **The controller** merged each approved workstream into `audit/integration`, resolved merge conflicts, kept a ledger of rulings, and ran the final verification on the merged code.
3. **Two final whole-branch reviews** of `audit/integration` at `423fa94` against `97467e8`, one for the backend half and one for the frontend half, on the most capable model available to the audit. They looked for problems no single workstream could see: interactions between merged changes, lost code in conflict resolutions, and weakened tests. Both re-checked the later fix rounds.
4. **The report writer** (this document) cross-checked the docs against the code and raised three gaps that were then fixed (WR-1 to WR-3 below).

### 2.3 Constraints that applied throughout

- **₹0.** Only free and open-source tools. No paid API, SaaS or licensed dependency. The one new dependency, `@axe-core/playwright` 4.14.0 (dev only), is MPL-2.0 and free. No cloud command that creates, starts, scales or changes anything; no load test against any cloud URL.
- **Local data only.** Every app run used PGlite in the agent's own worktree. The E2E suite recreates a throwaway PGlite database per run. W6 additionally ran a throwaway local PostgreSQL 18.4 cluster on `127.0.0.1:55150` (its own data directory) to read real query plans. The owner's system Postgres on `localhost:5432` was never touched; agents checked open connections with `lsof` before each server or E2E run, and the controller's final E2E run had a watcher that saw 0 connections to `:5432`.
- **Staging untouched.** Cloud SQL (`ros-pg18`) was stopped at the start and never started. No deploy and no `gcloud` write. `infra/gcp/deploy.sh` and `setup-ci-identity.sh` were edited but only checked with `bash -n` and `shellcheck`, never executed.
- **Git.** No push, no change to `main` or `staging`, no rewritten history. Migrations are additive with down files (`0008`, `0009`, `0010`).
- **Razorpay stays in test mode.** The `rzp_test_` guard in `packages/application/src/config/env.ts` is unchanged.
- **Severity scale (from the brief).** Critical: data loss, cross-tenant access, auth bypass, payment activation without verified payment, secret exposure. High: core workflow broken, privilege escalation within a tenant, realistic security weakness, offline action shown as done when it wasn't. Medium: wrong behaviour with a workaround, missing validation, bad error states, notable performance issue, accessibility blocker. Low: polish, naming, dead code.

### 2.4 Not in scope or not possible within the rules

Real phones and printers, a deployed staging run, the CI pipeline on GitHub, a real GA4 property, Search Console (no production domain exists), load tests against cloud URLs and a browser-driven Razorpay checkout. These are listed as coverage gaps in [regression-results.md](regression-results.md#10-coverage-gaps) and as owner actions where the owner can close them.

## 4. Consolidated issues

How to read the tables:

- **ID** is the identifier in the source report: `W1-01` (workstream report), `W1-R1` (that workstream's review), `W1-N1` (its re-review), `FB-F1` / `FF-F1` (final backend / frontend review), `FF-N-R2-1` (the final frontend reviewer's re-review of W6 round 2), `WR-1` (raised by the report writer). Where several agents found the same issue, it appears once and the other IDs are listed in the problem text.
- **Status**: **Fixed** (merged into `audit/integration`, commit given), **Open** (not fixed), **Owner action** (needs a setting or decision outside the code), **Declined** (fix rejected with a reason the reviewer accepted), **Accepted** (a known trade-off).
- **Proving test** names the test that fails before the fix and passes after it, unless stated otherwise. "CI only" means the test needs `PG_TEST_URL` and runs only in GitHub's `integration-pg` job; it was not executed during the audit.

## 9. Remaining risks

Ordered by impact. Owner actions are detailed in [manual-actions-required.md](../launch/manual-actions-required.md).

1. **The audit branch has never run in CI or on staging.** The `e2e` job (four production builds, 183 tests, then the consent run, `timeout-minutes: 30`) and the `integration-pg` job (with the new `postgres-resilience.test.ts`, never executed locally) run for the first time on GitHub. The `e2e` job runs on a push to `staging` (inside Deploy staging) or `main`, not on pull requests. `deploy-staging.yml` gates on the full CI, so a failure blocks the deploy rather than shipping.
2. **Rate limiting on Cloud Run stays shared** (W1-01) until `ros-staging-proxy-secret` exists and all four apps are redeployed.
3. **Pushing to `staging` runs migrations as the database owner** (W1-12) until branch protection is on.
4. **API JSON is not compressed on Cloud Run** (W6-P9): the guest menu is about 192 KB per load on phones. One read-only check decides whether Google's front end already compresses.
5. **Analytics must not be switched on** in any environment until Enhanced measurement is off on that stream (W5-M4) and the privacy text has had legal review (W5-M3, W5-N3). The code is inert without a Measurement ID, and the staging deploy refuses to turn it on without the explicit confirmation.
6. **Housekeeping and the 48-hour GA id cleanup run only from `/jobs/subscriptions`**, which nothing schedules yet.
7. **Migrations `0008`, `0009` and `0010` must be applied in order** (Drizzle skips a migration older than the last applied one). The index builds in `0009` and `0010` block writes to `bills` and `orders` for the length of the migrate transaction; deploy at a quiet hour once those tables are large.
8. **Kitchen behaviour now depends on the offline runtime starting.** The fixes (FF-F1, FF-F8) are tested in units and E2E, but not on a real kitchen tablet on a weak connection.
9. **Returning visitors keep the old service worker** on public and guest pages; the smaller footprint applies to new visitors (FF-N-R2-3).
10. **Not verified on real hardware:** phones, the 80 mm thermal printer, the kitchen display on its real screen, offline behaviour on real Wi-Fi drops.
11. **Production does not exist.** `deploy-production.yml` fails closed; domain, indexing variables, e-mail sender, legal entity and support address are not set (they are now runtime settings: `SITE_SUPPORT_EMAIL`, `SITE_LEGAL_ENTITY`).
12. **GA4 numbers will be lower bounds by design** (opt-in only; Cloud Run may drop a background send). Trials, revenue and activation must come from SQL.
