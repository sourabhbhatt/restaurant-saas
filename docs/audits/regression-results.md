## 2. Where the tests ran

- **All audit runs were local**, on the owner's Mac, each agent in its own git worktree under `.claude/worktrees/`, plus one CI run on GitHub Actions after the push (§12). Nothing ran on Google Cloud. Cloud SQL stayed stopped.
- **Databases.** Unit and integration tests use in-memory PGlite (PostgreSQL 18 compiled to WebAssembly) with every migration applied and row-level security on. The E2E harness (`tests/e2e/support/serve-api.ts`) recreates a throwaway PGlite database under `.data/e2e-<api port>/` per run, seeds it, and pins every provider (email outbox, local storage, no push, no payments, no tracking). W6's query-plan measurements used a throwaway local PostgreSQL 18.4 cluster on `127.0.0.1:55150`.
- **Safety checks.** Before each full E2E run the agents confirmed the API process held only files under its own `.data/e2e-<port>/pglite` and had no connection to `localhost:5432` (checked with `lsof`). The controller's final run had a watcher polling `lsof` every 5 s for established `:5432` connections; it recorded none. The harness refuses to write unless the API, console, ops and admin all report the run's random `APP_VERSION`.
- **Ports.** Each workstream had its own ports (W2 3110–3112/4110, W3 3120–3122/4120, W4 3130–3132/4130, W5 3140–3142/4140, W6 3150–3152/4150; final run 3190–3192 and API 4195), so runs never collided.
- **Do not use port 4190 (or any other Fetch "bad port") for the E2E API.** The controller's first final attempt put the API on 4190, which is on the Fetch standard's blocked-ports list; Node's `fetch` (undici) refuses to connect to it, so the frontends' proxy could not reach the API. Not a product issue. The rerun on 4195 passed.
